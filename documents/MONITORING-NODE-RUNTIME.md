# Separate Next/Node monitoring receipt path — source candidate, 2026-11-12

The existing Next application can execute this report/admission/recovery code using its Node runtime. It does not execute the Python worker. The new code does not accept a manual collection as canonical GitHub Actions evidence. The old Python importer, provenance policy, v1 renderer, v2 projections and stored originals are unchanged.

**Implemented:** bounded Node collection/projection, orchestration, receipt admission, source-history construction and immutable original recovery against injected contracts. **Unimplemented:** production deployment-bound writer authentication, trusted custody storage, current recurring-rights/identity bindings and scheduler. See [NODE-SOURCE-COLLECTOR.md](NODE-SOURCE-COLLECTOR.md) for the executable collector and its synthetic loopback acceptance. `getMonitoringRuntime()` always returns `null`; `/api/monitoring/run` and `/api/monitoring/recovery` return private/no-store 503 before input handling. No flag enables them. A READY application build is not hosted monitoring.

## Provenance is authenticated custody, not a fabricated Vercel signature

The separately versioned `vercel-next-custody-v2` receipt (with retained v1 admission/recovery) is a server-produced, content-addressed execution record. Admission retrieves the exact original from an independently trusted store; it never trusts posted source JSON, a success flag, or a caller-supplied receipt object. Every admitted record must have independently verified authorization for the actual writer and exact deployment/execution, immutable begin/completion custody, bounded chronology and matching scope/job/inventory/source/report digests.

This code does **not** yet supply that independent writer verifier. The injected `verifyExecutionWriter` is a required enforcement boundary, not proof merely because it returns true in a fixture. It must use protected external authority/custody evidence that is independent of the submitted receipt. An environment deployment ID matched to an approval list, or a project-only token, is insufficient. No signing key, token, deployment identity or provider attestation was created or read in this change.

Vercel documents signed OIDC identity claims for owner/team, project and environment, with issuer/audience/time claims. The documented claims do not bind a deployment/git SHA, execution nonce, source/report digest or HTTP result. System environment variables provide deployment/git metadata; they are not signed observation evidence. Sources checked 2026-11-12: [OIDC reference](https://vercel.com/docs/oidc/reference), [OIDC overview](https://vercel.com/docs/oidc), [system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables).

An eventual authenticated-custody implementation can establish that an approved runtime recorded particular bytes at a time. That still does not independently prove remote content truth, continuous availability, protocol compatibility, security, or execution of MCP tools. This origin is not equivalent to the separate GitHub Actions main/observe provenance policy.

## Distinct stages and identities

1. An authenticated worker supplies only a 64-hex job handle. The trusted job loader supplies account/mode/product, owner, canonical watchlist/version/slugs, period and fixed stage inputs. Rights must be current and exactly bound to that job and action; missing/unknown rights refuse execution.
2. The runtime independently authorizes its writer, allocates random execution/nonce IDs, and asks trusted custody to reserve both uniquely **before** capture or construction. The original start record binds job, inventory, runtime authority and evidence class.
3. A **capture** stage calls the implemented Node collector for at most two same-host watchlist inventory URLs, one robots request and 30 seconds. V2 can bind one independently admitted prior capture snapshot for conditional reads, cooldowns and last-success continuity. The adapter receives an abort signal and deadline; the runtime enforces a hard deadline and source execution/budget validation. It does not use request-supplied URLs or source data. Collector response processing/projection is implemented without invoking Python. Production routes remain unbound.
4. A **report** stage consumes at most 32 capture receipt handles from canonical server configuration. It independently admits their original custody records, verifies inventory/source content and prior-to-period-end chronology, and rejects duplicate execution, wrong stage, scope or changed identity. It calls the actual Node history producer and renderer, with a 2 MiB output bound and 60-second execution interval bound.
5. Completion stores the immutable original receipt plus capture source bytes or report bytes atomically. Only after integrity/admission and another current-rights check is the period index committed with compare-and-set. Concurrent or retried requests return the winning original. Duplicate computation can occur; this is not exactly-once collection.
6. Authenticated owner recovery validates the requested job index, exact stored job/execution, writer authorization, hashes and current recovery rights before returning the original bytes. It does not reload today's inventory, collect, load a new job configuration, or regenerate. It checks rights again after storage verification. A provider/storage outage refuses delivery rather than claiming deletion or absence of payment.

The custody store must enforce write-once begin/completion records, unique execution/nonce, immutable exact bytes, atomic job CAS and tenant/owner isolation under independently authenticated writer authority. The fixture store is single-process test infrastructure, not a production adapter or a durable serverless filesystem. Lost completion/index acknowledgements can leave unindexed originals; a future store's approved retention and cleanup policy must cover them. No hosted retention or billing rule is selected here.

Job periods are full-history snapshots as of period end, not a promise that every shown event occurred during the subscription period. Generate and recover rights are separate; tests demonstrate generation denied with recovery allowed, and recovery denied/unknown. These fixture decisions do not establish actual cancellation/refund/reversal policy.

## Preserved evidence semantics

`source-contract.ts` admits the existing source-v1/v2 structure, full catalog identity cohort, bounded projections, observation chronology, summary accounting and source identity/hash/date bindings. Node canonical JSON pins ASCII keys, escaped Unicode, safe integer numbers and a trailing newline; timestamps have at most millisecond precision. The separately named Node contract deliberately refuses ambiguous/unsupported representations; it does not rewrite old receipts. The source payload and custody receipt have separate hashes in report citations.

`history.ts` ports the existing deterministic comparison semantics: baseline, missing-at-check, recovery, inconclusive observations, last known success, retained findings, explicit freshness and cached-evidence deduplication. Section changes cite original capture dates, source URLs, both custody/source hashes and exact projection pointers. Full bodies are not republished. The report's aggregate heading/excerpt quote budget is 24 words per source, with explicit truncation/omission. Numbers, commands, destinations, preformatted whitespace and timestamps remain significant in the upstream projection; normalization is not a semantic judgment. Equal captured representation means other differences are unclassified. Unavailable/incomplete projections never become unchanged content.

New Node reports use `source-receipt-history-node-v2`, prioritizing the latest complete changed projection with balanced before/after quotes. The frozen Node-v1 renderer and original bytes remain supported. Stable period identity is deliberately independent of the current renderer policy; existing committed originals win retries. Neither renderer overwrites or re-renders a Python v1/v2 original. Existing Python source, original evidence and byte-recovery artifacts remain unchanged in this continuation.

## Executed source acceptance

All runtime acceptance uses **fictional observations, identities and authority**, including real loopback HTTP streams in the collector continuation. No Vercel function execution, public fetch, provider token verification, hosted ledger, customer identity, recurring right or payment is represented by these fixtures.

- The checked-in Python golden fixture was generated from fictional four-period HTML: initial Node 18, syntax-only attribute/entity changes, an incomplete 206 body, then Node 20/version/command changes. Node validation preserves all four exact canonical source hashes and matches the Python event/summary/document-comparison results.
- Real Node capture orchestration → custody admission → history/report construction → period commit → a separate Node process recovers identical original bytes, without collector/inventory/job-generation dependencies. The output clearly labels fictional execution/deployment identifiers.
- Regressions cover tampered receipt/source/report bytes, mismatched start metadata, missing originals, duplicate nonce/execution, wrong-stage/future/cross-owner inputs, changed indexes, lost acknowledgements, concurrent candidates, current-rights loss/unknown, original recovery after input change, capture/source budgets and default-off/bounded route behavior.

## Exact remaining hosted acceptance

The existing target is this repository's Next/Node Vercel application; no extra Python service is proposed. Before activation, the existing authority/storage owners must implement and independently review **deployment-bound writer verification and an authenticated immutable custody adapter** that satisfy the contract. Vercel's documented project/environment OIDC alone does not meet the deployment binding. If the approved platform cannot supply that binding, the evidence contract needs a further reviewed redesign; do not make the verifier unconditionally true.

The bounded Node collector/response projection adapter is now implemented with the retained allowlist, SSRF/TLS/robots, complete-byte and normalization contract. It can be wired as `collectCanonicalSources: createNodeCollector({ now })` after the independent authority/custody/rights bindings are implemented; source delivery alone is not collection attestation. Existing identity/commerce owners must supply canonical watchlists and exact recurring generate/recover rights, without treating the one-time kit as a monitoring subscription. No changes to those owners' files or services are included here.

Only after explicit collector/runtime/storage/rights/scheduling approval and adapter completion can a controlled hosted trial establish two genuinely separate observed periods, receipt admission/tamper refusal, immutable report recovery in a fresh authenticated session, owner isolation and revoked/unknown rights. A separate authorized sandbox lifecycle must verify payment → delivery → fresh-session recovery → cancellation/refund/dispute/reversal. No offer/price, cadence, retention or delivery promise is published by this change. Actual collected monitoring cash and MRR remain unproved.
