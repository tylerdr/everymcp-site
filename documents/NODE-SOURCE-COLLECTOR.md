## Concrete capture behavior

A canonical capture job selects one or two inventory URLs on **one allowlisted host**. Both URL membership and single-host scope are validated before DNS or robots requests. Other inventory sources remain in the report with their actual prior or unchecked states; selecting two sources is not coverage of the whole directory. Existing source admission rechecks full inventory identity, observation chronology and counters.

The new `vercel-next-custody-v2` receipt binds zero or one predecessor capture handle. The runtime independently admits that immutable original, requires completion before the new execution starts, then passes its validated source snapshot and current inventory to the collector. The collector cannot accept request-supplied cache contents. No recursive history crawl is required: each independently authenticated predecessor holds a complete source snapshot. V1 receipts still require zero capture inputs and remain readable; original v1 report bytes are recovered without rendering. Report citations identify the actual v1/v2 custody origin separately from source-payload hashes. Neither origin is GitHub Actions provenance.

A due source receives a new HTTP observation. Fresh-cache reuse does not become a new check. HTTP 304 uses only validated prior success and retains the original body-capture date and projection. Unknown, redirect, partial, oversized, malformed, blocked or timed-out responses cannot overwrite last known success or become unchanged content. HTTP 404/410 means missing at that check. The report keeps unresolved findings, dates and stale/unchecked state; it does not infer outage duration, MCP compatibility, tool behavior or security.

## Transport and policy bounds

- Canonical HTTPS/443 only, from the existing six-host allowlist. No credentials, query/fragment, encoded traversal, parser-repaired aliases, caller headers, cookies, authorization, followed redirects or decompression.
- Resolve all answers, reject the entire set if any answer is nonpublic, mapped, multicast, local or in conservatively excluded special-use ranges. One validated address is pinned through a custom lookup; no alternate-address retry or connection reuse occurs. Canonical Host/SNI and normal certificate verification remain enabled. The IPv6 acceptance range is deliberately conservative; a refused address is an unknown scanner outcome.
- A fresh proxy-free HTTPS agent and the built-in Node request parser enforce 16 KiB headers, strict framing and complete-body validation. Source bodies cap at 1 MiB; robots bodies cap at 64 KiB. Oversized, aborted, truncated or unsupported-encoding bodies are discarded and never hashed as complete content. No script, linked URL or MCP tool is executed.
- Each request has an absolute DNS-through-body timeout of at most eight seconds, bounded by the remaining capture budget. Cancellation is terminal: late DNS completion cannot open a socket. At most two source attempts and one robots request fit within the runtime's 30-second capture budget. Failed attempts count.
- Robots permission is checked before source requests, with at least one second between same-host requests and stricter parsed pacing honored. Restrictions that cannot fit the remaining budget skip the request. Redirected, malformed, unavailable-auth, unsupported-charset or otherwise uncertain robots responses do not grant permission.
- Source 403/429 stops the host immediately and preserves bounded cooldown evidence. Existing source retry policy clamps to 60–86,400 seconds. Because the retained robots receipt schema has no Retry-After field, robots 403/429 applies a conservative fixed 24-hour cooldown; the actual header is not invented in stored evidence. All active host-policy cooldown records survive intervening captures on other allowlisted hosts (at most six), without inventing a source observation.

Robots parsing is a **conservative subset**, not a full RFC-compliance claim. It merges equally specific matching product groups, uses the longest matching case-sensitive path rule (including wildcard/anchor length), and allows equivalent-rule ties. It supports `*`, terminal `$`, crawl-delay and simple request-rate. Encoded/non-ASCII rules, unsupported restrictions/windows or excessive matching work in applicable groups return unknown. Non-applicable groups do not override the selected policy. This stricter subset can reduce coverage until a separately reviewed parser extension is justified. [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html) defines the underlying group/path rules; [Node HTTPS](https://nodejs.org/docs/latest-v24.x/api/https.html) defines the transport interfaces.

## Useful document evidence

The Node projector consumes only already-read complete bytes. It retains `static-document-v1` hashes for the tested accepted subset: strict UTF-8 text/plain, text/markdown and HTML with strict stack/attribute handling. It uses the pinned Next bundle's MIT `TextNode` decoder for entities; it does not use a tree-repairing DOM parser. No new dependency was installed or declared.

Limits remain 16 sections, 20,000 tokens, depth 128, 64 attributes per tag, bounded names/values and 24 total heading/excerpt words with 160-character fragments. Text, numbers, versions, commands, destination attributes, preformatted whitespace and timestamps remain significant. Malformed or unsupported markup/decoder differences refuse a projection; excessive content becomes incomplete. Comments/scripts/styles/declarations have explicit omission categories. Equal projection says only that the captured representation is unchanged, with other raw differences unclassified.

Twenty-four fictional Python-generated cases match exact Node projection objects and hashes. Further cases cover each bound, Unicode/entity differences, changed link/version/command/whitespace/timestamp, malformed markup and validated 304 reuse. Old Python source and genuine artifacts remain unchanged.
